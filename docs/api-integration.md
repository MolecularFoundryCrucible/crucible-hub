# Crucible Hub API Integration

Status: Active integration contract

Date: 2026-09-16

## Authority and generated contract

This document owns Hub-side generated-client, server-function, Query, pagination, invalidation, and safe-error conventions. `crucible-api` owns paths, schemas, authorization, resource semantics, pagination shapes, and security schemes. Do not reproduce endpoint inventories or infer a missing contract. [`architecture.md`](architecture.md) owns runtime boundaries, [`authentication-transition.md`](authentication-transition.md) owns authentication cutover, and [Crucible API handoff](crucible-api-handoff.md#dynamic-hub-capability-plan) defines the proposed API additions for dynamic Hub destinations and workflows.

`contracts/crucible-api.json` is the reviewed deterministic input, `contracts/crucible-api.lock.json` records its source revision and digest, and `src/generated/crucible-api.ts` is deterministic generated output that is never hand-edited. `src/server/crucible/` is the server-only transport and adapter boundary; `src/data/crucible/` contains browser-safe models and Query options.

Contract refreshes must obtain an identified API revision, verify and lock the digest, regenerate with the pinned toolchain, review removals, required fields, unions, nullability, pagination, security, and deprecations, update adapters and tests, then run `npm run validate`. CI and production startup never fetch a moving staging OpenAPI document or regenerate output. An API mismatch is surfaced and coordinated with the owner, never silently repaired by Hub.

## Server-function boundary and errors

Browser-reachable code calls typed server functions and never imports API transport, session storage, credentials, or browser-configurable API origins. Every private function validates browser-safe input before invocation and at the server boundary, resolves trusted server and authenticated user authority, propagates abort signals, applies a bounded endpoint timeout, makes one generated operation or a small justified aggregation, and returns only a minimal browser-safe representation. Capabilities guide UI only, never authorization.

Feature code receives this stable envelope:

```ts
type HubApiError = {
  kind:
    | "unauthenticated"
    | "forbidden"
    | "not-found"
    | "conflict"
    | "validation"
    | "rate-limited"
    | "cancelled"
    | "timeout"
    | "upstream"
    | "unexpected"
  message: string
  correlationId: string
  retryable: boolean
  fieldErrors?: Record<string, string[]>
  retryAfterSeconds?: number
}
```

Hub creates a correlation ID for every document, server-function, and server-route request, places it in request context and `X-Correlation-ID`, and never trusts a browser value. Server functions return serializable `HubResult<T>` unions. The adapter maps validated failures to the envelope: 401, 403, 404, 409, 422, and 429 map to their named kinds; other HTTP failures are `upstream`; transport causes distinguish cancellation, timeout, and unexpected failure. It never exposes headers, cookies, authorization data, signed URLs, raw bodies, stack traces, or internal network details. Hub-to-API correlation propagation remains pending until the API publishes a supported header.

Failed server operations emit one structured diagnostic containing the Hub correlation ID, stable operation name, status, error type, and response-contract issue paths and codes when applicable. Logs exclude upstream response values and bodies, request values, credentials, complete URLs, and personal or scientific content. Cancellation is expected control flow and is not logged as a failure.

## Query ownership, representations, and hydration

TanStack Query is the sole browser owner of Crucible server data. Loaders use `ensureQueryData` or prefetch the exact options consumed by components, never a second representation. Every authenticated key begins with immutable identity scope:

```ts
type IdentityScope = readonly [
  "crucible",
  serverId: string,
  accountMfid: string,
]
```

Append stable MFIDs, representation names, and normalized primitive parameters. Slugs are lookup input only. Keys never contain credentials, signed URLs, user objects, client instances, unstable labels, or unnormalized filters. A server, account, login, or credential change replaces the active Query client before another identity renders. Persistence is disabled until a privacy and retention decision covers encryption, expiry, logout, and account isolation.

Collection, search, detail, relationship, file, and capability responses are distinct representations. Lightweight rows never seed or overwrite exact detail; tested projections may update compatible rows without erasing fields. Preserve public-safe and unavailable variants: null or omitted members or links are unavailable, while an explicit empty list is available and empty. Null capabilities mean guidance is unavailable, not denial. Expanded dataset project and instrument references are preferred; flat IDs are fallbacks.

SSR dehydrates only successful, defined, approved identity-scoped browser-safe Query families. Approved administration queries include only the non-secret service-account directory and detail representations needed by the active route. It excludes errors, session data, credentials, transient capabilities, unscoped data, unknown families, raw-search Queries, and one-time service-account keys. Public-safe person hydration may include only displayed name and canonical identity, never email or privileged account fields. A round-trip test must prove a fresh client hydrates only approved data.

Query functions pass cancellation through server functions and the adapter combines it with the timeout. Cancellation-sensitive content uses `useQuery` with local pending state, not Suspense hooks. A changed search or filter must abort superseded work and never render it as current.

## Reads, navigation, and pagination

Resource and project query keys identify their projection. Persistent resource shells and identity-only instrument lookups use a summary projection with resolved owner identity while omitting scientific metadata, relationships, and legacy embedded datasets. Resource Overview and the inspector use the canonical detail projection with links, metadata, and owner, while Graph, Manage, and Processing do not fetch those fields unless their own content requires the full representation. A cached canonical detail may satisfy a summary read without copying a lightweight row into detail. Project labels in filters, creation, search, and resource-carried project context use a summary projection without members or scientific metadata; the project workspace continues to use the canonical project detail with both includes. Withheld values remain unavailable rather than triggering fallback requests. Lightweight row name and type may render inspector pending identity without starting another detail request, and the inspector does not prefetch adjacent details or read neighbours recursively, files, downloads, counts, project members, collections, or every related row. At the server adapter boundary, `LinkedResource.direction` maps `source` to parent, `target` to child, and `undirected` to associated while preserving the nullable `relationship_type`. Lightweight relationship references provide only name, MFID, resource type, direction, and optional relationship type, so Hub does not issue per-row detail requests to obtain sample type or dataset measurement. Permission-filtered or unavailable links remain valid authorized data. [Decisions 0008](../decisions/0008-inspect-linked-resources-in-place.md), [0010](../decisions/0010-inspect-project-data-in-place.md), and [0012](../decisions/0012-inspect-global-data-in-place.md) define navigation behavior.

Resource Graph is an independent identity-scoped Query representation loaded only after entering a sample or dataset Graph route. The adapter calls `GET /resources/{resource_mfid}/graph` with an explicit depth and normalized direction, relationship-kind, and relationship-type filters, then validates the typed response and its root, bounds, node identities, edge identities, endpoints, relationship semantics, and required per-node expansion availability at the server boundary. Interactive views use lineage depth three. One Query follows upstream lineage, another follows downstream lineage, and a third depth-one Query loads the current root's direct associations; the view merges all responses by node MFID and edge ID. Keeping the two lineage directions in separate requests prevents traversal from moving upstream and then back downstream into a sibling branch. Expanding a node from its attached node control or the relationship table starts another independently cached depth-one Query rooted at that node, and the screen derives a merged graph without copying server state out of TanStack Query. The root requests and every expansion retain separate cache identities. The required `expansion_availability` booleans determine whether upstream lineage, downstream lineage, and association controls appear. When one node occurs in multiple responses, false is dominant for that channel because it proves all authorized matching edges were present in that response and therefore in the merged graph. A successful expansion removes its channel from the active view. The compatibility field `has_more_relationships` retains its request-scoped aggregate meaning. Graph truncation remains visible. Graph Queries neither seed exact resource detail nor request neighbour details. [Decision 0026](../decisions/0026-explore-bounded-resource-graphs.md) defines navigation and presentation behavior.

Signed file download capability is a user-activated transient POST server-function result, not a Query or Mutation result. The server calls the API only after activation, validates the currently untyped response strictly as one secure URL and positive lifetime, returns it with `Cache-Control: no-store`, and the browser immediately navigates in the same tab with no-referrer isolation. Hub never proxies or modifies the URL. It never enters HTML, DOM before activation, route state, caches, persistence, telemetry, logs, screenshots, or test artifacts.

Samples, datasets, projects, and instruments use cursor chains: omit `cursor` initially, follow returned `next_cursor`, and never mix offset into the chain. Full collection and directory reads request up to 100 rows and explicit authorization-filtered totals, while accepting a smaller API-returned page. Route search owns shareable filters and may contain a compatible initial cursor, while an identity-scoped TanStack Infinite Query owns appended pages, results, and refresh. An intersection observer requests the next page as the shared continuation row approaches the viewport, while the visible Load more action remains available for keyboard use, unsupported browsers, and explicit control. Automatic continuation stops after an error and resumes only through explicit retry. Appending never replaces readable rows or rewrites the URL. A canonical detail page opened from a collection retains the currently loaded lightweight sequence without copying it into route state. Its compact control identifies the active filter context and order without surfacing sequence positions or loaded-row counts. Previous and Next do not prefetch detail records; activating a known sibling loads that route normally, while activating Next at the loaded boundary calls the existing Infinite Query continuation once and appends the returned identities. The same control can rebuild a sequence around the current resource through two `anchor_mfid` reads with identical result filters and sort but opposite directions. The requested order supplies the following side, the opposite order supplies the preceding side, and Hub reverses that side and removes the duplicate inclusive anchor. Each anchored page uses its own Query key, omits the optional exact total, and continues its side through the returned cursor without resending `anchor_mfid`. Anchored reads never include cursor or offset. Missing or excluded anchors remain local errors and do not replace the current sequence. Changing a committed filter starts a new cursor chain and clears preview context. Global and project-scoped search are explicit-submit only. Project search passes the canonical `project_mfid` with `project_scope=all` to sample and dataset search operations. The application-bar search adopts active project context on project routes, project-scoped search results, and sample or dataset routes carrying a validated `fromProject`; its dialog keeps project and global scope explicit. `Ctrl K` always selects global search, while `Ctrl Shift K` selects the available project scope. Global scientific metadata search calls `GET /resources/metadata/search`, accepts only project, instrument, sample, and dataset results, groups them by type, and keeps raw search text out of dehydrated state and telemetry. Picker autocomplete searches debounce, use kind-bounded Query keys, and let superseded requests cancel through the existing Query transport. Essential identity uses `ensureQueryData`; recoverable collections prefetch and await only without readable cache data. Continuation failures remain local to the pagination action and preserve every successfully loaded page.

Each dataset or sample facet field, bucket order, and filter context owns a separate identity-scoped TanStack Infinite Query chain. Its key includes resource kind, field, API facet sort, API facet direction, and every normalized result-shaping filter; opaque cursors remain page parameters within that exact chain. A committed facet, ordering, or filter change starts a new chain, and a bucket set is complete only when `next_cursor` is null. Filter controls load facet chains only while their panel is open, retain exact stored text including empty strings, present null as a distinct selection, and exclude the controlled field from their own bucket request while composing all other filters. Browse views load the selected dimension's chain while visible and retain committed filters so they constrain the directory. Their sortable group headers default canonical labels to ascending and counts to descending, and toggle the active direction on repeated activation. Buckets display the API-provided canonical label while submitting the raw stable value as the exact collection filter. Selecting a concrete or null bucket starts the corresponding normal collection Query. The URL distinguishes no selection, an exact empty string, and null, and stores non-default group order or direction. Hub never parses facet cursors, groups or sorts an incomplete resource page as a complete collection, or eagerly loads every bucket's resources. The exact contract and bucket-to-collection mappings are in [Implemented dataset and sample facet contract](crucible-api-handoff.md#implemented-dataset-and-sample-facet-contract).

Dataset Processing owns independent identity-scoped file and ingestion Queries. Files load from `GET /datasets/{dsid}/files`; request history loads from `GET /ingestion_requests` with the canonical dataset MFID, a bounded limit, an explicit offset, and the API total. The server adapter validates both payloads at runtime so a contract mismatch becomes a local Query failure rather than invalid browser state. Hub joins each file to the first and therefore newest request returned by the API, presents raw unknown statuses safely, and does not infer successful ingestion from storage path. When the total exceeds the received page, an unmatched file has no recent status rather than a fabricated never-requested state. The bounded request page remains visible as history with its total.

The ingestion dialog loads available classes from `GET /ingestors` only when opened and always retains server-side auto-detection. Each selected GCS file creates its own request through the current `POST /files/{file_id}/ingest` operation with `status=requested`; Hub does not call the deprecated dataset-scoped ingestion path. Multi-file submission is explicitly non-atomic. Confirmed requests invalidate dataset ingestion history, while failed files remain selected with local recovery. The API independently authorizes each request because the current resource capability contract does not expose ingestion eligibility. Dataset-scoped post-processing remains unavailable until the API supplies dataset-specific process availability and durable request identity, status, outputs, and errors.

Do not fetch hidden types, sibling scopes, speculative tab counts, whole collections, or detail for every collection row. Home requests equally bounded sample and dataset pages ordered by creation time descending, merges those ordered candidates for Recently added, and never infers totals, relevance, attention, or scientific chronology from unsorted pages. Home separately requests bounded owner-affiliated projects and active instruments for Projects you lead and Instruments you manage. Those previews set `include_total=false`; the instrument preview also sets `include_owner=false` because its rows do not render the owner. Their View all links carry the same ownership scope into the full directory. The bounded Recently added union is valid because each source contributes at most the displayed result limit, but it does not define a pageable combined collection. Dataset and sample sorting may use the API's typed sort, direction, null ordering, stable ties, and order-compatible opaque cursors. Global Data therefore selects exactly one resource type and defaults `/data` to Samples. Type-specific Browse uses API-owned facet counts and exact collection filters; Hub must never sort, group, facet, filter, or paginate only loaded pages and present it as whole-collection behavior. Collection previews derive previous and next resources from the current type-specific loaded cursor chain. Crossing its forward boundary fetches that chain's next cursor page, while previous navigation is limited to retained pages and a URL that starts from a later cursor cannot recover earlier pages. Resource Overview and Graph register readable immediate relationships as one bounded neighbour sequence without loading more relationship data.

Global Data sends supported normalized ownership, project, scope, visibility, UTC creation-date, and dataset instrument filters before cursor pagination. Sample and dataset views, including project and instrument scopes, send typed server-side sort and direction values and expose Created as both a bounded filter and sortable column. Global Data has no All mode until the API provides a unified collection contract with equivalent query behavior. Apply commits URL state, resets relevant cursors and preview history, and Clear removes secondary filters without broadening malformed input. Drafts and chooser searches do not fetch collections. Dataset-only filters and type-specific sorting are removed when they cannot apply. Invalid or contradictory URL state receives local corrective feedback and never causes an unfiltered request. Applied filters are shareable history and in-memory Query-key data; drafts remain transient. Project and instrument directories expose a visible route-backed ownership switch, reset their cursor chain when ownership or lifecycle changes, append API-owned pages through the shared continuation, and request totals for visible loaded progress. The instrument directory keeps `include_owner=true` for its Owner column. Result-shaping options are part of Query identity so a compact dashboard response cannot replace a richer directory response. Their rows display API-provided Created and Updated values, but Hub omits Created sorting and time filters until those list operations accept matching query parameters.

Project Data uses canonical project MFID with explicit `all`, `assigned`, or `shared` scope. The API's omitted scope is not Hub's All default. All is the caller-readable project-access set; Shared is not inferred from assignment and can include unassigned or elsewhere-assigned resources. Contextual `project_relation` is not a resource property and never seeds detail. Scope and filters compose with API-owned AND semantics before pagination. Creation bounds use inclusive timezone-aware UTC values: `YYYY-MM-DDT00:00:00+00:00` and `YYYY-MM-DDT23:59:59.999999+00:00`. Never use scientific timestamp for creation date or invent request fields. All and Shared authorization failures stay local, without automatic scope changes or credential escalation. Instrument selection uses bounded confirmed instrument search, including inactive instruments, and label lookup cannot remove a filter.

## Mutations and invalidation

Use authoritative mutation responses for the same exact shape, merge only confirmed fields into rich detail, and invalidate the smallest dependent collections, relationships, summaries, and search views. Invalidate project or account views when membership, ownership, access, or assignment changes. No optimistic update for authority, provenance, deletion, upload completion, ingestion, relationships, or scientific metadata unless rollback is deterministic and cannot misrepresent state. Preserve drafts and partial success. Mutations require independent authentication, validation, same-origin, and CSRF enforcement.

Authenticated profile management reads and partially updates `/account/profile` through identity-scoped server functions. Hub validates changed first name, last name, email, and username fields, sends only changes, then rereads the account profile so capability guidance remains authoritative. It replaces the account profile Query, updates the matching public person identity without email, and invalidates cached representations that may embed the prior identity. The profile route separately reads `/account/verify` under its own identity-scoped Query to show only credential validity, creation time, and expiry; it never calls the existing-key retrieval operation. The authenticated email may appear only in the account-owned profile representation and must not enter public person results, persistence, URLs, logs, telemetry, or shared cache entries. Self-service credential rotation remains deferred until the API and Hub session boundary can replace server-held authority atomically.

Project creation uses `POST /projects`, requires a validated unique project ID, organization, title, and one resolved lead identifier, starts active, and navigates by the returned project MFID. Sample and dataset creation send `project_mfid` only when a project is selected. Dataset creation similarly sends `instrument_mfid` only when an acquisition instrument is selected. Hub does not also send the legacy mutable identifiers because the API resolves canonical MFIDs and requires paired identifiers to match. These creation requests require Crucible API revision `41eeed89c97b9a9108117499b628323f96189809` or a compatible deployment. Creation omits owner and `unique_id` and caches only confirmed detail. A confirmed API rejection retains an editable draft. An uncertain create outcome retains the draft, disables repeat submission while mounted, and directs the user to check Data because the API has no idempotency contract. Dataset-to-sample association is a separate duplicate-resistant stage; a confirmed dataset is never recreated to retry a failed link. See [decision 0025](../decisions/0025-let-api-assign-creation-mfids.md).

Resource Summary writes only documented changed descriptive fields. A capability-gated typed canonical route controls presentation, the API authorizes the patch, and recognized date-times round-trip between local controls and UTC. Nonstandard timestamp strings remain visible and untouched by unrelated writes. Project and instrument Overview editing likewise sends only dedicated descriptive fields, not lifecycle, ownership, access, members, operators, metadata, relationships, or deletion. Failed drafts are local, are never dehydrated, persisted, logged, telemetered, or placed in URLs, and use shared discard protection.

Dataset thumbnails use a separate identity-scoped Query key and are never folded into dataset detail or collection representations. `GET /datasets/{dsid}/thumbnails` supplies the ordered Overview gallery. `POST /datasets/first_thumbnails` supplies at most 100 deduplicated dataset MFIDs for Graph relationship previews; omitted results mean inaccessible or absent thumbnails and do not become errors. Reads begin after browser hydration and responses use `Cache-Control: no-store`. Add, rename, and delete require exact `can_edit` presentation guidance and use the API's POST, PATCH, and DELETE operations, followed by an authoritative thumbnail-list reread in API mode. Hub sends raw file base64 without a data-URL prefix, accepts source files up to the API's default 50 MiB limit, bounds names at 255 characters, replaces the complete thumbnail Query after confirmation, and confirms deletion. The API normalizes supported JPEG, PNG, WebP, TIFF, BMP, and GIF input to oriented RGB JPEG at no more than 512 by 512 pixels and quality 85. Thumbnail payloads remain memory-only and are not logged, persisted, placed in URLs, or loader-dehydrated.

Instrument directory queries always send one of active, maintenance, or decommissioned before offset pagination, with active as the URL-default view. Instrument Lifecycle uses `POST /instruments/{instrument_mfid}/status` and accepts only those three states at the Hub boundary. Exact `can_change_status` controls presentation, while the API authorizes the write. Decommissioning requires confirmation. The authoritative response must identify the target and contain a recognized status; Hub merges only confirmed status and modification time, applies no optimistic state, and invalidates instrument lists and search results. An unrecognized current status remains visible without becoming a selectable Hub-authored state.

Instrument registration uses `POST /instruments` with the API's exact 3 to 25 character instrument ID rule and required name, ID, and location. Hub omits owner, caches the returned instrument detail under its canonical MFID, and invalidates instrument collections and search. Service-account accounts do not receive the registration affordance, while the API remains authoritative.

Instrument Operators uses the instrument-specific list, add, and remove operations only when exact `can_manage_access` guidance is true. Candidate service accounts use the shared bounded person autocomplete backed by `GET /users/search` with `is_service_account=true`. Add and remove replace the complete returned list under an identity-scoped operator Query key. Removal requires confirmation. Internal group standing is not presented as an instrument permission.

Account-level capability guidance comes from `/account/profile` and controls creation and administration affordances without replacing API authorization. Service-account administration uses identity-scoped, no-store server functions for `GET`, `POST`, and role-specific `PATCH /service_accounts`, `GET /service_accounts/{unique_id}`, `PATCH /users/{user_id}`, and `POST /service_accounts/{unique_id}/rotate_key`. Directory search and offset pagination remain server-owned. Collection rows exclude key status, while exact detail reads may include only non-secret validity and timestamps. Create and rotate responses bypass TanStack Query and remain in mutation-local browser memory until the one-time credential dialog closes. The Hub does not call the existing-key retrieval operation. A role change accepts only None, Contributor, or Admin, is presented only to a human caller with service-account management capability, replaces exact detail from the non-secret response, and invalidates service-account lists. The UI does not imply immediate authorization propagation because API processes may retain prior authority through their configured authentication-cache lifetime, which defaults to 60 seconds. Contextual project membership caps service-account role choices at Viewer and Contributor in addition to the project's `max_grant_role`; the API remains authoritative because public search does not reveal platform-administrator role.

Ownership transfer uses `POST /resources/{mfid}/transfer_ownership` first without confirmation and then with `confirm=true`. Project assignment uses the equivalent preview-confirm sequence at `POST /resources/{mfid}/project`; the server adapter resolves the selected project MFID to its current project ID before both requests. Dataset acquisition-instrument assignment uses `PUT /datasets/{dsid}/instrument` with the selected canonical instrument MFID after local confirmation because the operation has no preview mode. Exact `can_transfer` and `can_manage_access` respectively guide ownership and assignment presentation, but the API authorizes every source and target. The instrument response must identify both the requested dataset and instrument. Confirmed fields may update exact detail, followed by resource, access, collection, facet, sibling-navigation, and search invalidation. None of these operations is optimistic.

Metadata writes accept a bounded root JSON object with JSON-compatible values only. Hub safety limits reject malformed values, non-finite numbers, blank or oversized keys, excessive depth or fields, and payloads over 1 MiB. Changed top-level additions and replacements use the shallow merge operation. Any top-level removal, including clearing the object, needs explicit full-replacement confirmation because the API has no conditional or atomic delete operation. Confirmed results update metadata only; no metadata write is optimistic. The HTTP representation cannot retain Python or NumPy runtime types. API producers must serialize NumPy scalars as JSON scalars and arrays as JSON arrays, and must reject unsupported values rather than emitting `{}`. Hub preserves a received empty object as `{}` because the contract provides no type marker from which the original value could be recovered.

Deletion uses the reviewed deletion-request operation, never direct permanent deletion. The optional reason is local and bounded. The response must identify the target; conflicts refresh detail so an existing request can appear. Do not infer deletion eligibility from edit or access capabilities.

Direct project membership is implemented in fixture and local API development through validated server functions for immediate add of an existing user, role change, removal, and non-owner self-leave. A full authoritative member-list response replaces, rather than client-merges, the cached membership representation. Capability guidance controls presentation, including grantable role and transfer constraints, but the API authorizes every request. Membership is separate from descriptive Settings, resource ACLs, ownership transfer, and join requests. There is no invitation workflow. Production exposure remains blocked until the accepted authentication exchange and Hub session boundary are deployed.

Relationship management is scoped to canonical sample and dataset pages. The source resource's exact `can_edit` capability guides presentation; the API authorizes both source and target. Add operations use an accessible bounded type search and explicit direction. Same-kind parent-child creation may optionally send `is_derived_from` or `is_part_of`, which always describes the child relative to the parent; cross-kind associations remain untyped. Hub omits the parameter for an unspecified new relationship and does not offer clearing because the API preserves an existing type when the parameter is omitted and publishes no clear operation. Unlink operations require confirmation and never delete either resource. The current adapter ignores legacy mutation bodies and rereads exact source and target detail with links before replacing both exact caches, with no optimistic update or unrelated collection refresh. Successful link and unlink operations also invalidate the exact graph Queries for both participants. Reject self-links and invalid pairs locally where deterministically known, while preserving API errors for duplicate, target, authorization, and cycle validation. The API gap remains explicit: relationship-specific capabilities, complete error and validation semantics, and typed authoritative add or unlink responses are required before production exposure. Development through the local API-key bridge does not waive the production authentication and session gate.

Resource management is route-backed at `/samples/:sampleMfid/manage` and `/datasets/:datasetMfid/manage` under the shared canonical resource parent. The parent shell and persistent header remain mounted across Overview, Graph, and Manage. ACL queries load only on Manage entry and set preload disabled. The exact `can_manage_access` capability controls access controls, including project assignment; exact `can_transfer` controls ownership transfer; reviewed deletion does not infer eligibility from either capability. Overview shows project context without that mutation control. Public controls remain distinct, and user or project grant roles are capped by the API-provided `max_grant_role`. Owner, service-account, instrument, system, and unknown grants are read-only. The primary-project grant is matched against the canonical project MFID, remains visible and read-only in Direct access, and changes only through the atomic project-assignment operation. Publish, unpublish, revoke, assignment, ownership transfer, and deletion requests retain their established confirmation behavior. Every write uses server-confirmed state, preserves readable data on failure, and makes no optimistic update. Legacy `/access` routes redirect to Manage.

Multi-stage workflows retain non-secret completed-stage checkpoints and retry only incomplete stages. Creation fields remain in memory and are not persisted in this package. A later failure never duplicates a created resource; secrets and signed URLs are reacquired.

## Validation

`npm run validate` verifies deterministic generation, drift, types, lint, token policy, secrets, and production build. Contract and adapter tests must cover input validation, safe error mapping, cancellation and timeout, cursor and offset behavior, detail-preserving cache behavior, approved hydration, and two-account client replacement. Browser tests use deterministic fixtures. Live authenticated services are not routine validation dependencies. The temporary local API-key bridge is development-only, rejected in production, and governed by [`authentication-transition.md`](authentication-transition.md).
