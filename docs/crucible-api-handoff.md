# Crucible API handoff

Open requests from Hub to `crucible-api`. Delivered requests are removed; the pinned contract (`contracts/crucible-api.json`, release in `contracts/crucible-api.lock.json`) is the record of what the API provides, and the [CHANGELOG](../CHANGELOG.md) records when Hub adopted it. Shapes below are proposals for discussion: the API owns final names, authorization, and semantics. Hub-side conventions are in [API integration](api-integration.md) and Hub delivery order in the [roadmap](roadmap.md).

## New capabilities

### Account pins

Durable per-account resource pins: `GET /account/pins` (cursor-paginated, newest first), and idempotent `PUT` and `DELETE /account/pins/{resource_mfid}`. Items carry the MFID, resource type, a permission-filtered identity summary, and `pinned_at`. A pin whose resource becomes unreadable returns a removable tombstone with only the MFID, or is deleted by a documented rule, and never leaks the old name. Pinning changes no authorization or timestamps.

### Account activity

One permission-filtered, cursor-paginated feed (for example `GET /account/activity`) so Hub does not merge join, deletion, membership, ingestion, post-processing, ownership, lifecycle, and upload records itself. Each event has an immutable ID, an enum type, UTC `occurred_at`, a public-safe actor, a canonical subject reference (MFID, type, name, permission-filtered project), a typed status or outcome, and a small typed details object rather than prose. The contract defines retention, redaction after access loss, and whether times mean request, transition, or completion. Polling a bounded first page is enough at first; push channels come only after replay and recovery are defined.

### Administration

- Navigation capabilities on `GET /account/profile` for destinations beyond users and service accounts, such as audit and processing operations, so Hub does not discover them by probing for `403`.
- A pending-work summary with authorization-filtered counts per category (join reviews, deletion reviews, failed processing), an `as_of` time, and explicit exact or capped precision, served separately from account identity. Hub currently counts join requests awaiting review with a one-row `GET /join_requests` read.
- A durable administrative audit log beyond `/deletion_audit` and sign-in history: operation, subject, permitted actor, time, previous and resulting state, and correlation reference, with scoped authorization, retention, redaction, filters, and cursor pagination. No credentials, signed URLs, or internal hostnames.
- Processing operations: typed ingestion statuses, safe failure codes, project and instrument filters, and explicit retry and cancel actions for ingestion requests (Hub does not use the generic `PATCH /ingestion_requests/{request_id}`), with idempotency defined.
- Saved views owned by the account, holding a versioned, validated filter and sort model rather than a URL or query language.

## Acceptance constraints

- The API remains the sole authorization authority and returns public-safe, permission-filtered representations.
- New behavior appears in a published OpenAPI release before Hub consumes it.
- Pagination, ordering, nullability, error, and concurrency semantics are defined wherever they affect Hub state or recovery.
- Normal Hub use never needs a standing platform-administrator credential.
