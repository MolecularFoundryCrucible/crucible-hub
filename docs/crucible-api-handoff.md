## Implemented dataset and sample facet contract

Status: Facet retrieval was implemented in `crucible-api` commit `300cd58`. Canonical bucket labels and configurable bucket ordering were added in commit `9ecd1c0`, introduced to Hub in staging revision `4833428aa269088098c59665327977515ab6d1bc`, and remain consumed through the pinned OpenAPI contract at revision `4c542221b7927d58d7ed3bc892e225bb81a2dc44` and generated Hub client.

### Operations and fields

| Operation              | Required `field` values                                                   |
| ---------------------- | ------------------------------------------------------------------------- |
| `GET /datasets/facets` | `session`, `measurement`, `data_format`, `owner`, `instrument`, `project` |
| `GET /samples/facets`  | `sample_type`, `owner`, `project`                                         |

`session` groups the stored dataset `session_name`. Project buckets group the canonical primary `project_mfid`, not every project that can read the resource. Instrument buckets group the dataset's canonical registered `instrument_mfid`, not its legacy free-text `instrument_name`.

Text values are grouped exactly as stored. The API does not trim, case-fold, or merge values, so `XAS`, `xas`, `""`, and null are separate buckets. Each non-null bucket includes a canonical display `label`. Text labels equal the stored value. Owner labels use full name, then username, then raw value; project labels use title, then project ID, then raw value; instrument labels use instrument name, then instrument ID, then raw value. Hub may provide contextual presentation labels for null, such as "Unspecified", "No primary project", or "No registered instrument", but must retain null as the query value and must not convert it to a sentinel string.

### Facet request parameters

All facet requests require `field`. They accept `sort=value|label|count`, `direction=asc|desc`, `limit` from 1 through 1000 with a default of 100, and an optional opaque `cursor` from the previous response. The defaults are raw value ascending.

Both operations accept these authorization and scope filters:

- Repeatable `accessible_to_user` and `accessible_to_project` selectors.
- Repeatable `affiliation`, currently supporting `owner`.
- `visibility=all|public|private`, defaulting to `all`.
- `project_id` or `project_mfid`, optionally with `project_scope=assigned|shared|all`; scope defaults to `assigned` when a project filter is present.
- Time bounds `creation_time_gte`, `creation_time_lte`, `modification_time_gte`, and `modification_time_lte`, each requiring a timezone-aware datetime.

Dataset facets additionally accept `sample_mfid`, `instrument_mfid`, `session_name`, `measurement`, `data_format`, `owner_id`, `session_name_is_null`, `measurement_is_null`, `data_format_is_null`, `owner_id_is_null`, `instrument_mfid_is_null`, and `project_mfid_is_null`.

Sample facets additionally accept `dataset_mfid`, `sample_type`, `owner_id`, `sample_type_is_null`, `owner_id_is_null`, and `project_mfid_is_null`.

Example first-page requests are:

```http
GET /datasets/facets?field=measurement&project_mfid=00000000000000000000000001&project_scope=assigned&limit=50
GET /samples/facets?field=sample_type&owner_id=0000-0001-2345-6789&limit=50
```

Facet requests do not accept resource sort, response expansions, offset, or exact-total controls. Counts include only resources readable by the authenticated caller and not excluded by the deletion policy after all supplied filters are applied. Unknown parameters, unsupported fields, invalid cursor context, invalid time ranges, a project scope without a project, and contradictory exact plus `is_null=true` filters return 422. An inaccessible or missing `sample_mfid` or `dataset_mfid` relationship filter returns 404. Project `shared` or `all` inspection retains the API's existing project authorization and access-group errors.

### Response shapes

Every successful response has this envelope:

```json
{
  "field": "measurement",
  "limit": 100,
  "items": [],
  "next_cursor": null
}
```

Text buckets contain the exact value, canonical display label, and authorization-filtered count:

```json
{
  "value": "XAS",
  "label": "XAS",
  "count": 42
}
```

Null has an explicit bucket and remains JSON null:

```json
{
  "value": null,
  "label": null,
  "count": 23
}
```

Owner buckets include the public-safe resolved account when available. The stable `value` may identify either a person or service account, and Hub must use `owner.is_service_account` rather than identifier format to distinguish them:

```json
{
  "value": "0000-0001-2345-6789",
  "label": "Ada Lovelace",
  "count": 12,
  "owner": {
    "unique_id": "0000-0001-2345-6789",
    "username": "scientist",
    "first_name": "Ada",
    "last_name": "Lovelace",
    "is_service_account": false
  }
}
```

Project buckets use the stable MFID as `value` and include the current resolved slug and title:

```json
{
  "value": "00000000000000000000000001",
  "label": "Battery Study",
  "count": 31,
  "project": {
    "unique_id": "00000000000000000000000001",
    "project_id": "battery-study",
    "title": "Battery Study"
  }
}
```

Instrument buckets use the stable MFID as `value` and include the current resolved identifier and name:

```json
{
  "value": "00000000000000000000000002",
  "label": "Beamline 8.3.2",
  "count": 17,
  "instrument": {
    "unique_id": "00000000000000000000000002",
    "instrument_id": "bl-832",
    "instrument_name": "Beamline 8.3.2"
  }
}
```

A null owner, project, or instrument bucket has `value`, `label`, and its resolved object set to null. A non-null value may have a null resolved object when legacy or inconsistent data no longer resolves; its label falls back to the raw stable value.

### Pagination and cache identity

Buckets can be ordered by raw stored value, case-insensitive canonical label, or count in either direction. Raw value is the deterministic tie-breaker for label and count ordering. Null remains last in every mode. The API returns at most `limit` buckets and sets `next_cursor` to null only at the end. Follow a non-null cursor on the same operation while keeping `field`, `sort`, `direction`, and every result-shaping filter unchanged. `limit` may change between pages. Cursors are signed and bound to the authenticated principal, resource kind, field, ordering, and filters, and cannot be reused across resource-list or different facet requests.

```http
GET /datasets/facets?field=measurement&project_mfid=00000000000000000000000001&project_scope=assigned&sort=count&direction=desc&limit=100&cursor={next_cursor}
```

Hub Query keys must include API server identity, authenticated account identity, resource kind, facet field, bucket ordering, and every supplied filter. The page cursor remains an Infinite Query page parameter. A committed facet, ordering, or filter change starts a new cursor chain. Do not parse cursors, derive an offset, merge buckets with different filter contexts, or claim a complete bucket set until `next_cursor` is null.

### Selecting a bucket

Use the normal collection route to retrieve resources for a selected bucket:

| Facet                 | Concrete bucket filter                  | Null bucket filter                           |
| --------------------- | --------------------------------------- | -------------------------------------------- |
| Dataset `session`     | `GET /datasets?session_name={value}`    | `GET /datasets?session_name_is_null=true`    |
| Dataset `measurement` | `GET /datasets?measurement={value}`     | `GET /datasets?measurement_is_null=true`     |
| Dataset `data_format` | `GET /datasets?data_format={value}`     | `GET /datasets?data_format_is_null=true`     |
| Dataset `owner`       | `GET /datasets?owner_id={value}`        | `GET /datasets?owner_id_is_null=true`        |
| Dataset `instrument`  | `GET /datasets?instrument_mfid={value}` | `GET /datasets?instrument_mfid_is_null=true` |
| Dataset `project`     | `GET /datasets?project_mfid={value}`    | `GET /datasets?project_mfid_is_null=true`    |
| Sample `sample_type`  | `GET /samples?sample_type={value}`      | `GET /samples?sample_type_is_null=true`      |
| Sample `owner`        | `GET /samples?owner_id={value}`         | `GET /samples?owner_id_is_null=true`         |
| Sample `project`      | `GET /samples?project_mfid={value}`     | `GET /samples?project_mfid_is_null=true`     |

Each `*_is_null` selector is optional. Omission does not constrain nullability, true selects null values, and false selects non-null values. A true selector cannot be combined with a concrete selector for the same field. Empty strings are concrete stored values and must be requested as empty values, not through the null selector.

Facet buckets are navigation and filtering metadata, not embedded grouped resource collections. Hub may render the bounded bucket list and lazily request a normal cursor-paginated collection for a selected or expanded bucket. It must not group one incomplete resource page and present those groups as complete, and it should not eagerly issue one resource request for every bucket.

### Deferred behavior

There is no calendar facet in this delivery. A future lifecycle facet should use API-managed `creation_time` in UTC with an explicit name such as `created_month`. Hub must not derive a server-wide month or year grouping from the producer-supplied `timestamp`, whose format and timezone are not enforced.

Hub cannot use it to atomically replace the upstream authority held by its server session.                   |
| Service-account administration | `GET` and `POST /service_accounts`, `GET` and `PATCH /service_accounts/{unique_id}`, `POST /service_accounts/{unique_id}/rotate_key`, and service-account-filtered user search support the current Hub Administration slice. Instrument operator routes and project membership routes support contextual assignment.                                                                                | Lifecycle status, disable or reactivate, key revocation without replacement, usage history, assignment summaries, administrative audit, and collection filters beyond search remain unavailable.              |

Deletion-request collection rows need public-safe `requester` and nullable `reviewer` identity summaries in addition to their stable IDs. The summaries should use the same compact person shape already returned elsewhere, including MFID, first name, last name, username, and service-account status. Resolving each row through `GET /users/{user_id}` would create up to one extra request per distinct identity, so Hub retains an MFID fallback until the collection contract embeds these summaries or provides a bounded batch resolver.

Self-service key rotation needs an authenticated server-to-server operation with a typed one-time result, explicit revocation timing, and defined session consequences. The Hub must replace its encrypted upstream authority and rotate the Hub session identifier before another request uses the old credential, then replace the active Query client. The API contract must also decide whether the replacement key may be returned once for external clients or remains exclusively server-held. The local environment-key bridge cannot support rotation because it must not acquire credential persistence or session behavior.

A suitable operation would be `POST /account/apikey/rotate`, authorized for the current account through the server-to-server Hub authority rather than an API-origin browser cookie. Its typed success response should contain the replacement `api_key` exactly once and the new `valid`, `created_at`, and `expires_at` status. The contract must state when the old key becomes invalid, whether the Hub login authority is independent from that key, and how a caller can recover from an uncertain response without rotating repeatedly. If the Hub authority uses the same key, the Hub session update and session-ID rotation requirements above remain mandatory before the response is exposed to the browser.

### Account capabilities and navigation

Extend the existing authenticated account capabilities with exact operation-specific guidance for the broader Administration proposal. A preferred shape is:

```json
{
  "capabilities": {
    "can_open_administration": true,
    "can_review_join_requests": true,
    "can_review_deletion_requests": false,
    "can_view_global_activity": false
  }
}
```

These values guide navigation and request affordances only. Every downstream operation must independently authorize the caller. Do not expose internal access-group IDs, magic group names, policy expressions, or a reusable platform credential as the browser-facing authorization contract.

If Hub should display pending-work badges, expose a bounded summary separately from account identity so volatile counts do not invalidate the account and session representation. The summary should return authorization-filtered counts by stable category, an `as_of` timestamp, and explicit exact or capped count semantics. Join-review counts must include every project the caller may review without requiring one request per project.

### Account pins

Provide durable per-account resource pins so the sidebar destination works across browsers and devices. Suggested operations are:

- `GET /account/pins?resource_type=&cursor=&limit=`
- `PUT /account/pins/{resource_mfid}` as an idempotent pin operation
- `DELETE /account/pins/{resource_mfid}` as an idempotent unpin operation

Each item should include the canonical resource MFID, resource type, a permission-filtered lightweight identity summary, and `pinned_at`. Sort by `pinned_at` descending with a deterministic tie-breaker and an opaque cursor bound to the authenticated account and filters. If access is later lost, return either a removable unavailable tombstone containing only the MFID and pin identity or define automatic deletion clearly. Never leak the prior resource name or project through an inaccessible pin.

Pin mutations should return the authoritative pin item or deletion result and define 401, 403, 404, and idempotent-repeat behavior. Pinning changes no resource authorization, ownership, modification time, or project activity time.

### Unified account activity

Provide one permission-filtered, cursor-paginated account activity feed rather than requiring Hub to merge ingestion, join, deletion, membership, lifecycle, ownership, upload, and future processing tables. A suggested read is `GET /account/activity?category=&project_mfid=&resource_type=&cursor=&limit=`.

Each event should contain:

- A stable immutable event ID and enum event type.
- Canonical `occurred_at` in UTC and deterministic cursor ordering.
- A public-safe actor reference when an actor may be disclosed.
- A canonical subject reference with MFID, type, display name, and optional permission-filtered project reference.
- A typed status or outcome where the event represents a request or process transition.
- A small typed details object defined per event type, rather than preformatted prose that Hub cannot localize or present accessibly.
- Optional canonical links or identifiers needed to open the relevant Hub page without N+1 lookups.

Initial event families should cover join requests, membership changes, ingestion requests, deletion requests, ownership transfers, instrument lifecycle changes, uploads, and future post-processing. Define retention, redaction after access loss, actor privacy, service-account representation, event immutability, duplicate suppression, and whether event times represent request, start, transition, or completion. Resource `modification_time` and project or instrument timestamps must remain separate from activity chronology.

Polling a bounded first page with conditional reads is sufficient initially. Server-sent events or WebSockets should be added only after the durable event model, authorization, replay cursor, disconnect recovery, and operational limits are established.

### Join-request submission and review

Keep the existing account and reviewer list operations, but strengthen `JoinRequestRead` and `JoinRequestReview` so Hub can implement project-level pending state, Activity review cards, and approve or reject dialogs without identity lookups.

`JoinRequestRead` should include:

- Stable request ID.
- Stable project reference with project MFID, current project ID, and title.
- Public-safe requester and nullable reviewer references.
- Enum status such as `pending`, `approved`, `rejected`, `cancelled`, and `expired`, restricted to states the workflow actually supports.
- Request reason, reviewer notes, requested time, reviewed time, and an optional version or precondition value.
- The membership role that approval will grant or the bounded roles a reviewer may choose.
- Exact `can_review` and `can_cancel` guidance where the same representation serves different callers.

Prefer a canonical project-MFID submission path over exposing the internal access-group name as project identity. Add an exact current-account request read scoped to one project, or allow `/account/join_requests` to filter by project MFID, so a project page can show Request access, Pending, or the resolved result without scanning account history.

Review input must constrain the transition to supported enum values. Approval should atomically create the membership and access-group state, then return the reviewed request plus the authoritative resulting project membership. Rejection should return the reviewed request. Define duplicate submission, concurrent review, already-resolved, withdrawn, project-deleted, requester-already-member, insufficient reviewer authority, 403, 404, and 409 outcomes. A pending requester should be able to cancel when policy allows. Retried reviews must be either idempotent for the same outcome or return a typed conflict that lets Hub refresh safely.

### Administrative review workspace

The detailed proposed Hub routes, contextual project and instrument surfaces, capability model, API shapes, cache effects, delivery stages, and acceptance criteria are documented in [`administration-workspace.md`](administration-workspace.md).

Admin is a separate capability-gated destination. Its first useful scope should be bounded review work rather than a generic database console:

- Pending deletion requests and deletion audit.
- Join requests visible through the caller's platform or project-lead authority.
- Failed or stuck ingestion and future processing requests when the caller has the corresponding operational authority.
- Public-safe user and service-account lookup only where a defined administrative workflow needs it.

Every queue should use enum filters, deterministic server-side ordering, opaque cursor pagination, exact or explicitly capped totals, stable canonical subject references, and typed operation-specific capabilities. Review mutations should support stale-write protection and return authoritative reviewed objects. Audit entries should identify the operation, subject, permitted actor reference, timestamp, previous state, resulting state, and correlation reference without exposing credentials, signed URLs, internal hostnames, or secret paths.

Admin eligibility must come from the account capability contract. Receiving 403 from an admin endpoint is valid enforcement but is not a navigation-discovery mechanism. Normal Hub requests must continue using the authenticated person's authority and never a standing platform-administrator credential.

### Collection summaries, saved views, and navigation badges

The staged collection sorting and `include_total` work is the foundation for dynamic Data, Project, and Instrument pages. Follow-up contracts should add:

- Authorization-aware project sample and dataset counts with explicit assigned versus shared semantics.
- Authorization-aware instrument dataset counts with explicit acquisition-instrument semantics.
- Additional bounded server-side facets only after their field meaning, cardinality, resolution, null behavior, and filtering semantics are defined. Dataset session, measurement, data format, owner, instrument, and project facets and sample type, owner, and project facets are deployed on staging and pinned by Hub.
- Stable saved views owned by the authenticated account, containing a versioned validated filter and sort model rather than an arbitrary URL or query language.
- Anchored bidirectional sibling navigation for a canonical current resource within a saved, supplied, or newly configured collection context. The response must preserve authorization scope, filters, grouping selection, sort order, deterministic tie-breaking, and stable cursor semantics without requiring Hub to scan preceding pages. Ordinary navigation that starts from a loaded Hub page can continue forward through its known cursor chain without this addition.
- A lightweight navigation summary for pending join reviews, deletion reviews, failed processing, or other actionable categories, with exact or capped count semantics.

Do not update resource or container modification timestamps to simulate activity, counts, or attention. Do not require Hub to load whole collections, merge incomplete pages, or issue per-row requests to construct these summaries.

### Dataset processing and post-processing

Complete the Dataset Processing destination with a typed dataset-scoped process contract:

- `GET /datasets/{dataset_mfid}/processes` with cursor pagination and stable request identity.
- `GET /datasets/{dataset_mfid}/processes/available` or equivalent capability-aware operation discovery.
- `POST /datasets/{dataset_mfid}/processes` with a typed process kind, validated parameters, and idempotency support.
- `GET /processes/{process_id}` and a supported cancel or retry operation where the processing system can guarantee those semantics.

Process representations should include enum status, request, start, update, and completion times, requester, input file or dataset references, output resource or artifact references, bounded progress when meaningful, typed failure information safe for users, implementation version, and exact available actions. File ingestion should likewise expose enum statuses and operation-specific retry guidance. Neither workflow should require Hub to infer process availability from names or reconstruct lifecycle from logs.

### Suggested API delivery order

1. Strengthen join-request schemas, stable project and person references, review results, and exact reviewer capabilities so Hub can expose submission and review using existing operations.
2. Add account capability guidance so Activity and Admin navigation can be exposed without policy inference.
3. Add durable account pins.
4. Add the unified activity feed and pending-work summary, initially using bounded polling and conditional reads.
5. Harden deletion review and audit contracts for the first Admin queue.
6. Deliver remaining authorization-aware counts, then saved views and any additional demonstrated facets.
7. Add typed dataset post-processing availability, requests, and results.

## Acceptance constraints

- Preserve API authorization as the sole authority and return public-safe, permission-filtered representations where appropriate.
- Publish deterministic OpenAPI artifacts and compatibility evidence before Hub consumes new behavior.
- Define pagination, ordering, nullability, error, and concurrency semantics where they affect Hub state or recovery.
- Do not require a standing platform-administrator credential for normal Hub use.
