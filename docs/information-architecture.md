# Crucible Hub Information Architecture

Status: Active route and navigation contract

Date: 2026-09-16

## Purpose and authority

This document owns Hub routes, navigation, shell behavior, page archetypes, and responsive interaction. [Product brief](product-brief.md) owns user intent and workflows; [architecture](architecture.md) owns runtime and data boundaries; [roadmap](roadmap.md) owns delivery order and evidence. The proposed cross-workspace Administration and contextual project or instrument management expansion is specified in [`administration-workspace.md`](administration-workspace.md).

## Navigation principles

- Use stable MFIDs in canonical paths and preserve validated URL state for collection views.
- Keep global navigation, entity context, and local section navigation visibly distinct.
- Preserve collection context when opening a canonical resource and when using the optional resource inspector.
- Show authorized public-safe representations as valid content, not as failed loading.
- Use direct links for navigation and native browser history, new-tab, and modifier-key behavior.

## Application shell

### Global destinations

| Destination | Purpose                                                                     |
| ----------- | --------------------------------------------------------------------------- |
| Home        | Continuation, bounded summaries, and actions available to the current user. |
| Projects    | Project discovery and project workspaces.                                   |
| Data        | Cross-project samples and datasets.                                         |
| Instruments | Instrument discovery and workspaces.                                        |
| Search      | Cross-resource search and MFID lookup.                                      |
| Requests    | Account submission history and authorized deletion review.                  |
| Activity    | Proposed account-relevant activity when the API contract is available.      |
| Account     | Profile, preferences, and session controls.                                 |
| Admin       | Capability-gated administration, currently for service accounts.            |

Wide layouts use a persistent sidebar and top utility bar. The top utility bar provides one global Create menu linking to dedicated project, sample, dataset, and eligible instrument creation routes without inferred context. Contextual creation actions remain on project and instrument surfaces because they carry explicit project or instrument preselection. Shortcuts, Theme, and the expand or collapse action form a utility group at the bottom of the sidebar. Expanded navigation shows their labels; collapsed navigation keeps vertically stacked icons with named tooltips. Keyboard navigation includes global destinations plus contextual Overview, Graph, and Manage destinations where those sections exist. Narrow layouts use a drawer or bottom navigation with the same destinations and route structure. Global navigation never duplicates entity-local sections. Entity pages expose their current name in the browser title and place an explicit Refresh action at the right edge of their section-navigation row. The action refreshes the canonical project, instrument, sample, or dataset representations used across the entity workspace. Its accessible label and tooltip name that scope, and the tooltip presents the browser-local time of the last successful read. Independently loaded Graph, Processing, file, thumbnail, and access data retain section-local refresh and recovery behavior.

Home presents recently added data plus separate bounded ownership sections for Projects you lead and active Instruments you manage. The ownership sections use server-side `affiliation=owner`, omit exact totals, retain API order, and link View all to the equivalent filtered directory. Recently viewed follows recently added data in the primary Home column while the two ownership sections share the adjacent column on wide screens. Recently added merges bounded sample and dataset results by creation time as one account-scoped snapshot. It waits for both sources before its initial presentation and retains the previous snapshot while either source refreshes so independently completing requests cannot reorder a partially populated list. Recently added and Recently viewed use one resource-row structure with the resource icon and name, icon-labelled project ID and monospaced MFID below, and a creation or last-viewed timestamp aligned opposite. Recently viewed uses only server-and-account-scoped React state owned above route error recovery so routine navigation cannot discard it. It retains at most eight project, instrument, sample, or dataset identities, displays five on Home and the newest four as direct sidebar shortcuts, never enters URLs or persistent browser storage, and resets on reload or account replacement. The expanded sidebar places Recent after capability-gated Administration. The collapsed sidebar represents the same bounded list with one history action and an anchored menu so recent entries never displace administrative navigation.

## Entity scopes

### Account

The application-bar avatar opens the account menu and links to My profile and Deletion requests. The profile route presents the authenticated account identity in a read-first view and links to the same request history. Authenticated and public person profiles show the shared icon-labelled Crucible ID with its quick-copy action. Edit profile opens first name, last name, email, and username controls backed by the self-service account operation. Email remains private to the authenticated account view and profile mutation. Account access presents assigned platform role, current privilege mode, and Administrator-view availability separately from capability checks, which always reflect the currently effective API capabilities. At wide widths, Profile and Account access form the first row while API credential status sits directly beneath Profile at the same width. Status, Created, and Expires share one row inside the wide credential card. Compact layouts stack Profile, API credential, and Account access in that reading order. Credential rotation remains unavailable until it can replace the server-held upstream authority and active Hub session safely.

### Project

Project routes retain project identity, breadcrumbs, and local navigation while a child section loads. Data is the index and switches between Samples and Datasets; All, Assigned, and Shared are collection filters rather than separate project identities. Rows show their actual primary project and resource detail remains canonical.

The project collection is a compact responsive directory with linked project identity, Lead, Created on wide layouts, Updated, and a trailing full-page action. Its route-backed ownership scope switches between All and Led by me and starts a fresh cursor chain when changed. Pages append through the shared automatic and explicit continuation, with loaded progress and Back to top. A missing title falls back to project ID. Minimal API rows present unavailable Lead, Created, and Updated values as `-`; Hub does not fabricate sample or dataset counts when the collection contract does not provide them. Lifecycle state is omitted because it does not help distinguish rows in this collection.

Project navigation has Data and Overview plus capability-gated Manage when membership or ownership operations are available. The persistent project header owns the title and project-prefilled sample and dataset creation actions. Overview contains one read-first Project details section with project ID, organization, lead, MFID, Created, and Updated; authorized people can explicitly replace that card with descriptive editing for title, organization, and project ID. A separate scientific metadata section and read-only People section follow. The People section links authorized users directly to Manage and presents the authorization owner as Lead. Manage is one page with direct member addition, allowed role changes, and confirmed removal in Access management. A bounded project-filtered deletion review card appears for project management roles and links to the shared request workspace. Resource management contains preview-confirm ownership transfer followed by destructive confirmed self-leave. These actions remain distinct from resource ACLs and future join requests. Former Members and Ownership URLs redirect to Manage. No invitation workflow or top-level Members destination exists. A non-member can receive a public-safe project representation without membership-only fields.

The exact project endpoint returns `ProjectWithLead`: `unique_id`, `project_id`, `title`, `organization`, `project_lead_orcid`, resolved `lead`, `status`, `creation_time`, `modification_time`, `members`, `scientific_metadata`, and nullable `capabilities`. Hub renders the resolved public-safe lead in preference to its identifier, uses capabilities only to expose valid actions, and omits the project status badge from the project header. Optional values remain absent or use the standard empty presentation rather than being fabricated.

Project creation is a dedicated route linked from the project collection. It requires a project title, validated project ID, organization, and an existing lead. The current account is the initial lead and bounded people search can replace it. New projects start active and open by returned canonical MFID.

Project-scoped search uses the canonical project MFID to find related samples and datasets across assigned and shared relationships. The application-bar search visibly adopts project scope across the project workspace, project search results, and sample or dataset routes reached with validated project context, and labels the action with the resolved project title or project ID. Its dialog makes This project and All Crucible explicit, while `Ctrl K` selects global search and `Ctrl Shift K` selects project search. The search breadcrumb and Back to project action return directly to Project Data, and canonical resource links retain the project for contextual return navigation. A dedicated application-bar QR action scans a valid raw MFID or trusted Crucible resource link, passes the extracted MFID through the API-backed type-resolving resource route, and then opens the canonical entity page. Global search also offers a URL-backed Scientific metadata mode that searches API-provided full-text metadata results and groups supported resource types without presenting loaded-page filtering as complete search.

### Instrument

The instrument directory provides URL-backed Active, Maintenance, and Decommissioned views using API-side status filtering before pagination and links accounts with the registration capability to a dedicated registration form. A route-backed ownership scope switches between All and Managed by me, composes with lifecycle status on the same control row, and starts a fresh cursor chain when changed. Pages append through the shared automatic and explicit continuation, with loaded progress and Back to top. Results use a compact responsive directory with linked instrument identity, Location, Owner, Created on wide layouts, Updated, and a trailing full-page action. An absent name falls back to instrument ID and then MFID. The selected lifecycle view supplies status context, so individual rows do not repeat status badges. Registration requires name, a valid instrument ID, and location, omits owner so the API applies the authenticated person, and opens the returned canonical MFID route. Instrument routes retain identity and local Data and Overview navigation plus capability-gated Manage when a lifecycle, operator, or ownership operation is available. Data contains the instrument-scoped dataset collection. Overview presents the description inside a read-first semantic Summary with an explicit descriptive edit action for authorized people, an Identity card with the instrument ID, copyable MFID, QR code, abbreviated owner, and local timestamps, and full-width expandable scientific metadata. Manage has independent Lifecycle, Operators, and Ownership subsections according to exact capabilities. Operators uses service-account-only autocomplete and confirms removal. Ownership uses the API preview and explicit confirmation. Lifecycle offers active, maintenance, and decommissioned states through the dedicated API operation, with explicit confirmation before decommissioning. Dataset scope is the API-defined acquisition instrument across readable projects. Hub does not imply a direct project-to-instrument relationship.

The Administration sidebar group and service-account management links remain visible to a human profile with `authorization.can_elevate`, even when normal-mode `can_manage_service_accounts` is false. It also links to the shared Needs review deletion-request view. Deletion review retains the selected global privilege mode, while service-account routes apply contextual elevated authority automatically and show a Platform administration indicator without changing the global access mode. Their directory uses server-side search and offset pagination, reflows into labelled compact records on narrow screens, and never derives effective authorization from principal type. The detail route shows profile identity, platform role, and non-secret credential status. Profile edits use the standard explicit edit state. Human administrators can explicitly change the platform role to None, Contributor, or Admin; the confirmed response replaces exact detail, dependent lists refresh, and the interface states that authorization propagation may take about a minute. A service account's public person page links to this administrative detail for an eligible human administrator. Eligible human administrators can open the same route-backed service-account creation dialog from either the directory or the shared Create menu. Creation and confirmed rotation may return an API key once; the key remains only in the active dialog and is cleared when the dialog closes. The Hub offers no retrieve-existing-key, suspension, or deletion action without a dedicated API contract. A labelled switch above the Administration destinations separately exposes Administrator view and condenses to an identifiable pressed icon with the sidebar. It uses shield-minus for standard access and shield-plus for elevated access, with the active collapsed control using the warning surface. When active, its persistent top-bar action indicates that routine collections, search, detail, and mutations use elevated authority until the user turns it off or the browser session ends.

### Resource

Resource detail has a persistent identity header and type-specific content for summary, identity, dataset thumbnails, files, relationships, scientific metadata, processing, access, and allowed actions. At wide widths, Overview uses independent vertical stacks: Summary and Files occupy the wider leading column, Identity and Thumbnails occupy the narrower trailing column with the standard section gap, and Relationships and Scientific metadata share an equal-width row below them. Narrow layouts keep each stack together and omit dataset-only sections for samples. Summary includes descriptive fields followed by the current linked project and, for datasets, acquisition instrument. Dataset thumbnails and the compact downloadable file list load as separate browser-initiated representations. Relationship groups use one vertical flow within the half-width card. Scientific metadata uses a row-based JSON tree with first-level collections expanded, deeper disclosures collapsed, types and nesting preserved, and one header control beside Edit for expanding or collapsing the complete tree. Thumbnail editing exposes explicit add, rename, and confirmed delete controls only when `can_edit` is true. Actions stay local to the affected section and preserve readable content during refresh or recovery.

Sample and dataset creation use dedicated routes reachable globally and from project context; project context may preselect an optional project, and instrument context may preselect optional dataset acquisition. Both omit caller-assigned MFIDs, initialize the editable timestamp from the current browser-local minute, and keep descriptive values in place after validation or request failure. Both forms keep all fields visible in one card with consistent primary details, type-specific details, and Relationships sections. Relationships use the same supported parent, child, cross-type, and optional relationship-type vocabulary as canonical resource pages. Canonical navigation uses only the API-assigned MFID. An uncertain structural create disables repeat submission and directs the user to check Data because the API has no idempotency contract. Structural creation completes before queued relationship mutations. If any relationship fails, the form locks the confirmed resource stage and offers recovery for only incomplete relationships before canonical navigation.

Sample and dataset routes use a shared parent shell with the persistent resource header and route-backed Overview, Graph, and Manage navigation. Datasets add Processing between Overview and Graph. The breadcrumb shows the resource's canonical primary project. A validated optional `fromProject` search parameter preserves project context across resource sections, while browser history provides chronological return navigation without a separate back action consuming header space. Collection resource previews use a non-modal right inspector at wider widths so the underlying page remains interactive, while compact full-page presentation retains modal behavior. The inspector presents type, name, MFID, and the full-page action as one identity block. Processing, Graph, and Manage data load only when their tab is entered and are not intent-preloaded. Graph display preferences share the resource URL and control canvas-only association visibility, dataset thumbnail previews, and layout orientation without changing the complete relationship table. Dataset Processing follows the Access management pattern as one page with Files and ingestion followed by Dataset processes. Files and ingestion joins dataset files to their newest reported ingestion request, retains full request history, and submits selected eligible files independently so confirmed requests survive partial failure. Dataset processes remains empty until the API provides durable request identity, status, outputs, and dataset-specific availability. A future dataset viewer route uses one stable viewer ID beneath the dataset workspace and lists only API-advertised typed representations supported by the build-time viewer registry. Manage remains available because deletion eligibility has no capability guidance. Public, direct-grant, primary-project assignment, and dataset acquisition-instrument assignment controls require `can_manage_access`; direct grants and the public control share one access card, with direct access first. User and project grants are bounded by `max_grant_role`. Owner, service-account, instrument, system, and unknown grants are displayed read-only. The canonical primary-project grant remains visible with a Primary project indicator and is also read-only because project assignment owns its role and lifecycle. Publish, unpublish, and revoke require confirmation, and access failures remain local to their section. Project assignment, dataset acquisition-instrument assignment, capability-gated ownership transfer, and reviewed deletion share one resource management card while remaining distinct operations. Ownership transfer uses server preview before explicit confirmation. Reviewed deletion retains a destructive action and remains available without inferring eligibility from unrelated capabilities.

Project assignment appears in sample and dataset Manage when `can_manage_access` is available. Overview Summary shows the current primary project without presenting an authority-changing control. Assignment selects a project by stable MFID, resolves its current project ID at the server boundary, previews the atomic grant and assignment move, and requires explicit confirmation. Dataset acquisition-instrument assignment appears beside it under the same presentation capability. It selects a registered instrument by stable MFID, confirms the current and selected identities locally, then uses the dedicated atomic API operation so the canonical instrument fields and derived instrument-group grant change together.

The Relationships section is the canonical management surface for supported sample and dataset links. It states direction explicitly for parent-child and cross-type associations. Add uses an accessible dialog with bounded search constrained to the supported target type. Unlink requires confirmation and removes only the relationship. The section uses the source resource's exact `can_edit` guidance for local controls, while the API authorizes both resources and validates the pair. Relationship controls are absent from the inspector.

The Graph tab is a read-only alternate representation of a sample or dataset's bounded readable relationships. It keeps the resource header and tab navigation mounted while loading locally. After the initial bounded reads settle, ELK Layered calculates the layout in a browser worker, arranges lineage from parent to child from top to bottom at every viewport width by default, keeps the current resource centered on initial layout, separates nodes without overlap, and renders direct sample-dataset associations as dashed undirected edges. Horizontal orientation remains an explicit display option. The initial graph follows ancestors and descendants through separate depth-three one-direction traversals while retaining only the current resource's immediate associations. This avoids automatically showing sibling branches reached by moving upstream and then downstream; multi-hop association and sibling branches appear only after explicit expansion. Selecting a related node opens the existing overlay inspector without resizing the graph; Open navigates to canonical detail and Explore from here reroots the Graph route on that resource. Nodes can be dragged to refine the current arrangement, reset to a fresh ELK layout, and viewed through the browser's native fullscreen surface. Nodes with confirmed additional readable topology directly expose the available bounded expansion controls beside the node, with equivalent actions in the relationship card. Each expansion is a separate depth-one read merged by stable node and edge identity. Confirmed complete nodes and successfully checked directions do not show their corresponding controls. The graph preserves readable content during loading, reports arranging state, animates layout updates unless reduced motion is requested, and keeps the focused resource stable while new topology is placed. A server-limited graph reports its incomplete state. The relationship card provides the same identities, typed directions, relationship labels, inspection, canonical navigation, expansion, and bounded dataset thumbnail previews without requiring pointer interaction or graph interpretation. Large results render incrementally and defer thumbnails until the table nears the viewport. Thumbnail failure does not block the graph. Relationship changes remain on Overview rather than turning the visualization into an editor. [Decision 0026](../decisions/0026-explore-bounded-resource-graphs.md) defines the bounded interaction, and [resource graph API handoff](resource-graph-api-handoff.md) records the implemented API and layout boundary.

### Resource inspector navigation

An optional `preview` search parameter opens a sample or dataset in a right-side overlay above the current resource, project Data, or global Data page. The host page remains mounted, retains its geometry and scroll, and owns collection filters and cursors.

Opening from a closed panel creates one browser-history entry. Following another preview replaces that entry while a bounded in-preview trail supports Previous preview from the inspector top bar. Previous preview returns to the host when the trail is empty. Close returns safely to the host state while preserving its current scroll position. Direct preview entry and reload have no trusted trail. Canonical Open links navigate to the full resource page without leaking unrelated host search state. Invalid, unavailable, denied, loading, and failed previews remain local to the overlay.

The inspector is non-modal without a backdrop when the underlying page remains visible and modal at compact widths where it covers the page. Escape and non-interactive outside dismissal close it safely, while focus movement alone does not dismiss it and an underlying link or control completes without a competing history transition. Focus returns to the trigger when possible. The inspector does not reserve persistent layout space or fetch collection rows, files, adjacent resources, or every related detail. Known row identity replaces a generic pending heading.

Opening a canonical sample or dataset from a loaded collection starts an account-isolated, session-only sibling sequence. Overview presents one outlined Browse nearby action when no sequence exists. An active sequence replaces it with a compact grouped control beside section navigation, combining icon-only Previous and Next actions with a clickable filter context and order. Sequence positions and loaded-row counts are not surfaced. Left and Right Arrow keys work only while the Overview control is mounted and outside editable fields and overlays. The sequence retains lightweight MFID, kind, and name values plus Query-owned continuation. It reuses loaded rows and lets the selected canonical Overview route own its normal detail request. The middle action opens a focused configuration dialog for all readable resources, the same primary project, measurement or sample type, owner, or dataset instrument and for name, creation-time, or update-time ordering. The dialog can also clear an active sequence. Applying configuration rebuilds a bounded two-sided sequence around the current MFID through opposite-direction anchored reads, then fetches only the direction whose loaded boundary is reached. Graph, Processing, and Manage preserve the opaque history token without exposing sibling controls, so returning to Overview restores the sequence. Reloads and account changes omit the in-memory sequence.

## Page archetypes

| Archetype               | Required behavior                                                                                                               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Dashboard               | Bounded continuation data, local recovery, direct canonical navigation.                                                         |
| Collection              | Validated URL state, cursor pagination, lightweight rows, local loading and recovery, and responsive table-to-list containment. |
| Entity detail           | Persistent identity context with independently loading sections and local mutation feedback.                                    |
| Form or guided workflow | Explicit validation, retained drafts, cancellation and unsaved-change handling, and recoverable partial completion.             |
| Interstitial            | Clear permission, missing-resource, or service-recovery guidance without masquerading as empty content.                         |

Page composition assigns semantic width by responsibility. Forms and identity-management lists use the reading boundary, compact actions use capped adaptive tracks, entity detail cards use normal DOM order in the shared wide and narrow grid, and tables or graphs retain workspace width. Responsive layout changes columns without changing reading, focus, or screen-reader order. Optional cards collapse through normal grid placement rather than reserved rows.

Sample and dataset collections use one collection toolbar for resource type, filters, and grouping where those controls apply. Global Data switches directly between Samples and Datasets, defaults `/data` to Samples, and does not present a combined All mode because the API has no unified retrieval, sorting, filtering, or pagination contract. `Group by: None` presents the flat list, while selecting a supported facet opens the API-backed group directory and loads resources only after one group is selected, using the corresponding exact or null collection filter before cursor pagination. Group directories show canonical API labels and expose the displayed dimension and Count as sortable headers. Names default ascending, counts default descending, and the active header can reverse direction without changing the selected group or resource-list cursor. A reserved Count column remains visible while long group labels truncate with their full value available on hover. Global Data supports sample type, measurement, session, data format, owner, instrument, and primary-project dimensions where they apply. Project Data omits the redundant primary-project dimension, and Instrument Data omits the redundant instrument dimension. Selected resources default to API-side newest-created order unless the URL specifies another resource sort. Filters open in a viewport-bounded side sheet with an independently scrollable body and persistent Apply and Clear actions, so the collection does not reflow while filters are edited. The URL owns the selected resource type, view, dimension, group ordering and direction, selected value or explicit null bucket, committed filters, resource sorting, and resource cursor. Sample and dataset tables expose separate Created and Updated columns, with server-side Created bounds and sortable Created headers. Project and instrument directories display both timestamps but defer corresponding sorting and filtering until their list operations provide the same query contract. Wide layouts place the group directory beside the selected group's normal resource table; narrow layouts stack the directory and results in the same reading order. Cursor-backed collections expose one Back to top action after the page heading scrolls out of view, returning focus to that heading without changing collection state. Hub never combines, groups, or sorts incomplete cursor pages or eagerly loads one resource page per group.

## Responsive and accessible behavior

- Keep routes and semantic headings unchanged across widths.
- Prefer stacked controls, horizontally contained data regions, and card or list fallbacks over page-level horizontal overflow.
- Use visible labels, semantic controls, keyboard-operable dialogs, and non-color state cues.
- Preserve focus and announce local loading, failure, and mutation state without replacing stable page context.
- Keep status, permission, lifecycle, and resource type understandable in text as well as color or icons.

## Route validation scenarios

- Deep-link, refresh, Back, Forward, and new-tab navigation preserve canonical identity and appropriate collection state.
- Parent entity identity remains visible while child sections load or recover.
- Collection filters and preview state do not cause unnecessary collection reads or cross-host state leakage.
- Public-safe, empty, denied, missing, loading, and failed states are distinguishable.
- Narrow layouts, keyboard navigation, focus restoration, and theme parity retain the same route behavior.
