# Crucible Hub Design System

Status: Phase 0 baseline

Date: 2026-09-06

## Scope and principles

This document owns Hub tokens, themes, component policy, responsive behavior, accessibility, and visual validation. [`product-brief.md`](product-brief.md) owns product intent, [`architecture.md`](architecture.md) owns runtime boundaries, and [decision 0003](../decisions/0003-owned-design-system.md) owns the decision to use an owned system.

Hub is a desktop-first scientific workspace that shares Lens's semantic hierarchy and state discipline, not its phone dimensions, Compose structure, navigation, or Material defaults. Use semantic meaning before appearance, calm dense rows and tables, explicit accessible states, native HTML before managed primitives, usable full MFIDs, and one behavior contract across light and dark themes. Accessibility is a release property.

## Ownership and tokens

| Layer                                | Owner                        | Primitive values           |
| ------------------------------------ | ---------------------------- | -------------------------- |
| Primitive scales and semantic themes | `src/styles.css`             | Allowed only here          |
| Controlled shadcn primitives         | `src/components/ui`          | Shared tokens only         |
| Crucible domain components           | `src/components/crucible`    | Semantic tokens only       |
| Feature screens and routes           | `src/features`, `src/routes` | No primitive visual values |

Generated primitives enter `components/ui`, are reviewed, and become Hub-owned source. Feature code must not introduce colors, arbitrary utility values, shadows, type sizes, spacing, radii, breakpoints, z-index values, or motion durations. A missing role is a design-system change, not a local exception.

Primitive scales use a 4 px base and named spacing roles, repository-pinned self-hosted Noto Sans plus system monospace for MFIDs, shared radius and elevation roles, named layers, and named responsive breakpoints. Semantic utilities own each typography role completely: feature code does not recreate roles with primitive Tailwind size, weight, line-height, or tracking utilities. Use tabular numerals for changing data, selectable monospace MFIDs, and no interface text below 12 px.

| Role                                      | Size / line height / weight | Use                      |
| ----------------------------------------- | --------------------------- | ------------------------ |
| `title-page`                              | 28 / 36 px / 600            | Route title              |
| `title-entity`                            | 24 / 32 px / 600            | Entity title             |
| `title-section`                           | 18 / 28 px / 600            | Section, dialog, group   |
| `body-prominent`                          | 16 / 24 px / 400            | Spacious body and inputs |
| `body`, `identifier`, `label`             | 14 / 20 px / 400 or 600     | Rows, MFIDs, controls    |
| `supporting`, `label-compact`, `overline` | 12 / 16 px                  | Secondary content        |
| `metric`                                  | 24 / 32 px / 600            | Bounded summary          |

Top-level read-only field labels in Summary, Identity, Context, profile, and management cards use the 14 px semibold `label` role with muted foreground. Their values use the 14 px regular `body` or `identifier` role with normal foreground. Reserve the 12 px `supporting` role for hints, secondary identifiers, dense scientific metadata keys, and supplementary status text.

Person identity uses the shared `PersonIdentity` presentation primitive. `inline` shows the full or first-initial name for dense fields, `stacked` shows name over normalized `@username`, and `avatar` adds an initial avatar to the same two-row identity. Human avatars use the person-colored border, while service accounts use the semantic service-account orange border around the same neutral fill and retain the `Service account` secondary label so the distinction does not rely on color. The API account-type field is authoritative. Avatar identities use the predefined small, default, or large sizes. Missing names fall back through supplied display name, username, and MFID; missing usernames use consistent unavailable copy. Resource identity uses `ResourceIdentity` for the semantic type icon, display name, optional context, and optional MFID in stacked and collection presentations. `PersonLink` provides canonical person navigation with the shared `IdentityHoverCard` interaction shell wherever a person identity is linked. `ResourceIdentityLink` uses the same shell only for project and instrument references inside sample and dataset lists or detail pages, where previewing context avoids interrupting the data workflow. Project and instrument identities on their own directories, Home, search, access, and other primary navigation surfaces remain direct links without hover previews. Hover previews repeat the entity identity, place the fixed-length MFID on its own non-wrapping full-width line, then show only context already available to the current surface. They open on pointer hover or keyboard focus, while activation follows the canonical link directly on every input type. They suppress browser-native title tooltips so browser and operating-system rendering cannot compete with the shared preview. They supplement visible identity and never contain information required to navigate or understand the row. Chooser buttons use display-only identity primitives so selection does not unexpectedly navigate. Other navigation uses the canonical preview and full-page link components so presentation never chooses a route. `MfidText` owns identifier typography wherever copying is not offered, while `MfidValue` adds the standard copy action.

Use 44 px minimum primary touch controls. Dense pointer-oriented rows may be 36 px only when each target is at least 24 by 24 px, separated, and keyboard reachable. Semantic layout roles include page gutter, content and reading widths, section gaps, dense pill roles, and a 320 px initially resizable metadata editor. Use restrained 4, 8, 12, and 16 px radius roles only after fixture calibration. Resting elevation is `level-0` flat, `level-1` sticky or raised, `level-2` menu or popover, and `level-3` modal. Prefer surfaces and borders to decorative shadow.

Use quick, standard, and deliberate motion roles with initial 120, 180, and 240 ms targets. No continuous decoration. Reduced motion removes non-essential transforms, parallax, auto-scroll, and continuous effects. Shell breakpoints are compact below 48 rem, medium at 48 rem, wide at 64 rem, and expanded at 80 rem; components prefer container queries. Named layers cover base, sticky, navigation, popover, modal, notification, and emergency messages.

Themes use calibrated OKLCH values and foreground/background pairs for background, surface, card, popover, primary, secondary, muted, accent, destructive, success, warning, info, border, input, action border, ring, selection, sidebar, and data visualization. Resource pairs cover sample, dataset, project, instrument, person, file, and service account. Person identity uses cyan-teal, distinct from project blue, instrument orange, dataset green, and sample purple. Renderers that cannot parse OKLCH use theme-matched companion tokens serialized in a format they support. State, type, permission, and lifecycle always also use text, icon, shape, position, or pattern. Do not derive hierarchy with arbitrary foreground opacity.

Light, dark, and system preferences share these roles. Resolve theme before first paint, set `color-scheme`, react to system changes only in system mode, and persist only the preference, never derived colors. Any browser preference must be account-neutral and safely cleared or recomputed on identity change. Validate every semantic pair in both modes.

## Primitives and components

[Decision 0006](../decisions/0006-use-base-ui-primitives.md) selects Base UI. Pin it in `components.json`, use the official shadcn CLI and registry, inspect current documentation and project context, preview changes, and never overwrite Hub modifications without review. Use composition and existing variants first. Community registry components require provenance, dependency, license, source, accessibility, and theme review. Do not switch primitive base or preset as a feature side effect.

Install primitives only when needed and treat `src/components/ui` as the current inventory. Do not document a planned component as installed. Keep layout composition at call sites and semantic visual variants in shared components.

Lists use flat full-width rows or semantic tables. Cards are reserved for contained groups, summaries, empty states, and bounded metrics. Metadata uses the shared full-width tree renderer: at most six top-level fields before disclosure, first-level collections expanded on resource pages, deeper native disclosures, explicit counts, monospaced scalar values, indentation guides, and explicit null or empty labels. The inspector's metadata remains closed initially.

### Content composition

Card and section width follows content responsibility rather than the amount of available page space or the current amount of data. Shared composition components under `src/components/crucible` own these roles while the shadcn Card primitive remains content-agnostic.

| Role        | Content                                                          | Layout behavior                                                                          |
| ----------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Action      | A short explanation and one launcher or consequential action     | Capped track that shares an adaptive row with peer actions and stacks on compact layouts |
| Reading     | Forms, access lists, members, operators, and prose               | Full width up to the semantic reading boundary                                           |
| Wide detail | Summary, identity, files, relationships, and structured metadata | Four-column or three-column span within the shared seven-column detail grid              |
| Workspace   | Tables, search results, files, and graphs                        | Full available content width with local containment where needed                         |
| State       | Missing, unavailable, and recovery content                       | Existing centered state boundary                                                         |

Detail grids and action clusters use normal DOM order and CSS Grid auto-placement. Responsive changes may alter columns and spans, but must not use CSS `order`, explicit row placement for optional content, duplicated markup, or masonry behavior. Capability-gated and type-specific omissions collapse naturally without empty cells. Action cards retain intrinsic height and their controls preserve geometry through ready, pending, failed, and unavailable states.

Domain components accept semantic data and actions, never authorize or infer permissions. Presentational components do not fetch. The first layer includes resource, project, instrument, person, and MFID identity; capability actions; status; metadata; relationship rows; collection names; Summary and Settings editors; scientific metadata editor; collection state; and bounded query-backed chooser. The chooser owns at most one identity-scoped kind-bounded search and transient dialog state, never route state, committed filters, enumeration, or authorization. Picker inputs use the shared autocomplete, debounce bounded searches, and show selectable results in an anchored overlay so results never reflow the surrounding form or its actions.

Use a semantic icon catalog, not arbitrary feature imports. The shared resource and principal type icon component owns icon selection and semantic color, and call sites supply only layout classes. Canonical project, instrument, sample, and dataset headers place this icon directly before the wrapping resource name without a redundant type eyebrow. Resource names use the available header track before wrapping, while descriptive prose retains the reading-width boundary. Sample type and dataset measurement remain in Summary instead of being repeated beneath the title. Summary values use a shared field-icon mapping, with colored semantic icons for linked projects and instruments and neutral icons for descriptive fields. Identity values use a shared field-icon mapping for MFID, visibility, owner, and timestamps; the Owner field selects the person or service-account principal icon from the resolved owner type. Decorative icons are hidden from assistive technology. Icon-only controls have persistent resource-specific accessible names and visible tooltips, and are reserved for obvious low-risk actions. Text remains for unfamiliar, destructive, ambiguous, or qualified actions. Resource and critical-state assignments are stable. No emoji, logo, or brand mark is a normal UI icon. Lucide is the configured icon library; local SVG additions require review through the same catalog.

The application shell uses the square Crucible Hub logo as sidebar artwork and browser favicon, separate from the semantic UI icon catalog. The standalone Crucible Hub icon remains available for reviewed brand uses that do not need the logo background. Crucible dark blue, light blue, and orange have dedicated brand roles. A softened light-blue surface identifies the light sidebar, dark blue identifies the dark sidebar, and orange marks the current destination boundary. Brand colors do not replace resource-type or state colors. The expanded desktop sidebar uses a 16rem reading width and keeps Shortcuts, Theme, and Collapse navigation as standard labeled menu rows in its footer. The collapsed sidebar centers the logo on the same column axis as its navigation and footer icons. It retains the current-location treatment and presents the same footer utilities as vertically stacked icons with named tooltips. Only the compact drawer trigger remains in the application bar. The brand label uses the 1rem semantic brand role; sidebar destinations and route-backed resource section navigation use the 0.875rem body and label roles.

Action variants preserve the surface hierarchy. Primary actions use the filled primary pair. Secondary actions use the filled neutral pair for selected or moderate emphasis. Outline actions use the neutral action surface and stronger semantic action border, so they remain distinct from the canvas, cards, and raised surfaces in both themes. Ghost actions have no resting container and are reserved for low-emphasis actions whose placement and label make their affordance clear. Destructive actions use the destructive pair and an explicit label so risk never depends on color alone. Destructive entry points also use an icon when it helps distinguish the action. Confirmation footers do not repeat trigger icons; they show only action text and a temporary progress icon while pending. Hover states may change the action surface but must retain its paired foreground. The shared Button primitive and its `buttonVariants` helper are the only sources for general action typography, surfaces, borders, radii, internal spacing, heights, and icon sizing. Both paths return the same resolved class list. Feature-level `className` values may control external layout such as width, flex behavior, alignment, or position, but must not replace visual or sizing rules. Search and chooser result rows use the shared selection size, responsive collection links use the shared table-action size, and sidebar utilities use SidebarMenuButton rather than restyling Button. The design-token check rejects raw buttons and visual Button overrides outside shared UI primitives. Shared class composition recognizes every semantic typography role as a font-size utility so foreground utilities cannot replace it. Cards use the card surface with a restrained boundary; popovers and dialogs use the raised popover surface with stronger elevation.

Resource cards use filled, full-height buttons for the primary workflow available from a section, including adding a member, operator, access grant, or relationship; publishing; choosing a project; and choosing a new owner. A destructive workflow uses the same size and placement with the destructive variant. Read-first edit modes, utility actions, downloads, and secondary navigation use outline or ghost actions with compact icon-only controls only when the icon has a persistent accessible name and tooltip.

Forms use the default variant for their commit action and outline for cancel actions. Filter controls use secondary for the selected value and ghost for unselected values. Retry and refresh controls use outline because they support the current view rather than advance its primary workflow.

Instructional copy, confirmations, and tooltips emphasize a referenced resource's displayed name with semantic strong text so it remains distinguishable from the surrounding action or relationship wording. Accessible names remain complete plain-language actions.

## Interaction policy

- Use distinct semantics for navigation and disclosure chevrons. Selected navigation exposes current location beyond color, applies `aria-current` to the current destination, and uses the orange brand role for its active boundary. Persistent desktop navigation collapses to an accessible drawer or bottom pattern without changing route identity. Route-backed resource section navigation uses shared 2.5rem targets and the semantic 0.875rem semibold label role for every tab. Inactive tabs gain a visible fully rounded neutral surface and normal foreground text on hover. The active tab retains normal foreground text and adds a separate square-ended orange underline. The row sits closer to the preceding header divider than ordinary page sections, and contextual creation actions align at its right edge when space permits. The global Create control remains available at every supported width and uses a keyboard-operable menu of direct route links; contextual creation remains a direct link with explicit preselection.
- Sidebar utilities use the same menu-row primitive as primary navigation. Theme opens a radio menu for System, Light, and Dark rather than cycling without feedback. The Shortcuts dialog lists global search, project search, sidebar, navigation-sequence, help, and dismissal keys. Keyboard shortcuts do not activate while a person is typing in an editable field or interacting with a dialog.
- Every form control has an accessible label. Shared fields provide semantic grouping, validation association and announcement, and distinct required, optional, disabled, read-only, pending, and failed states. Drafts survive failure until success or explicit discard. Read-first editable cards use `EditableCardActions`, which owns the outline Cancel action, primary Save action, form association, disabled behavior, pending label and progress icon, and text or compact icon presentation. Creation forms retain workflow-specific footers because their submit actions may navigate or advance multiple stages.
- Summary edits may replace editable values within their card without changing page identity. Sample and dataset Summary also keeps read-only linked project and acquisition-instrument context visible. At wide widths, Resource Overview uses independent vertical stacks: Summary and Files use the wider leading column, while Identity and Thumbnails use the narrower trailing column with the standard section gap between each pair. Relationships and Scientific metadata share an equal-width row below those stacks. Compact layout keeps each stack together before Relationships and Scientific metadata. Relationship groups use an auto-fitting layout and collapse to one column when their container is narrow. Dataset thumbnails use an uncropped contained image on the card surface, a visible caption, lazy loading, and a separate edit state with explicit add, rename, and destructive delete controls. Project details and instrument Summary use the same explicit read-first editing pattern and shared field, local-error, pending, and discard behavior. Project and instrument Manage use one page without nested navigation. Access management contains project members or instrument operators, with the primary add action below the list and removal controls exposed through an explicit management mode. Resource management contains ownership and leaving for projects, and lifecycle and ownership for instruments. Leaving uses destructive treatment and confirmation. Registration is a dedicated form route. Consequential previews keep the selected target and resource name visually distinct, preserve fixed action geometry while pending, and require explicit confirmation. Keep lifecycle, ownership, access, members, operators, metadata, relationships, assignment, registration, and deletion separate.
- Metadata edit mode uses a bounded vertically resizable monospace root-JSON workspace. JSON types and nesting round-trip. Removing a top-level field requires full-replacement confirmation until the API supports atomic deletion.
- Member role badges name the role and communicate hierarchy by order. A project owner is presented as Lead in project membership surfaces while the underlying authorization role remains `owner`. Unknown roles use a neutral fallback. Member management uses a focused add dialog with explicit person selection and a persistent confirmation action, explicit automatically saved role edits, and confirmation for removal or voluntary leave. Direct membership has no invitation workflow and production exposure remains blocked on session authentication.
- Relationship management belongs to canonical resource pages, not the inspector. At widths where the underlying page remains visible, the inspector is a non-modal complementary surface without a backdrop, so the collection and navigation remain available; an outside interaction dismisses the inspector while allowing the underlying action to proceed. At compact widths where the inspector covers the page, it retains modal focus and backdrop behavior. A dedicated top bar keeps the outlined Previous preview action on the left and Close on the right. Previous preview follows the in-panel trail when one exists and otherwise returns to the host page. Content begins below this bar with the resource icon beside the wrapping resource name, followed by a dedicated left-aligned icon-labeled MFID row and a centered full-width action for opening the canonical page. Type-specific values remain in Context rather than repeating in the header. Relationship rows keep the wrapping identity and canonical action on one row at every width and omit a redundant resource-type subtitle. The Relationships card groups the outlined Graph navigation action with its primary Add action and compact outlined Manage utility. State parent-child and cross-type direction in text and use a focused accessible dialog with bounded target-type search for add. Normal rows expose only canonical navigation; an explicit management mode replaces the navigation action with unlink controls, and unlink uses an alert dialog for confirmation. Controls follow the source's exact `can_edit` guidance but must not imply that either resource will be deleted. Keep pending, invalid, duplicate, self-link, cycle, unavailable, and failed states local and understandable without color.
- Resource Manage is a route-backed child of canonical sample and dataset pages with a persistent parent header and Overview, Graph, and Manage navigation. Do not preload ACL data before Manage entry. Show access controls, including project assignment, only for exact `can_manage_access`; place direct grants before the public-access control in one access card, cap user and project grant choices at `max_grant_role`, and render owner, service-account, instrument, system, and unknown grants as read-only. Place project transfer, ownership transfer, and reviewed deletion in one resource management card while retaining a destructive treatment for the deletion action itself. Ownership remains capability-gated, and reviewed deletion remains available without inferring eligibility from unrelated capabilities. Consequential operations use explicit confirmation and server-confirmed feedback without optimism. Overview Summary context remains descriptive.
- Consequential actions use confirmation and API preview where available. Pending, unavailable, failed, and ready controls preserve exterior geometry and use accessible feedback inside the reserved action area.
- Bounded cards and contextual panels use `CollectionRowsPending` when row-shaped content is loading, `PanelState` for empty or initial-error content, and `PanelUpdateError` when readable data survives a refresh failure. These states stay within the owning card or panel so its stable heading and surrounding page structure do not refresh with API content.
- Resource identity includes a complete selectable MFID that uses the full card width, stays on one line when the compact viewport permits, and retains the shared fixed copy action in detail and inspector surfaces. Absent Summary values use `-`. Recognized timezone-aware ISO and PostgreSQL-style API timestamps display in browser-local time as abbreviated month, day, year, and 24-hour hour and minute, such as `Sep 6, 2026, 14:32`. Normalization accepts the API's space separator, microsecond precision, and compact UTC offsets without interpreting timezone-free values. Native local date-time controls own editing; unrecognized values stay unchanged and are never guessed.
- Confirm selectors to a record rather than storing arbitrary labels. Filter drafts use Apply and Clear, stay separate from URL state, name lifecycle field and time zone, and never call scientific timestamps creation dates.

Semantic table markup is the default with TanStack Table controlling headless state. Use semantic column-width roles, bounded primary-name cells with complete accessible values, keyboard-operable URL-backed controls, and virtualization that retains focused row and position access. Compact layouts may reflow the same semantic table rows into labeled stacked records, use an explicitly equivalent item list, or use bounded table scroll, never page-wide horizontal scroll. Do not duplicate interactive table content solely for a breakpoint. Do not imply unsupported bulk actions. File rows reserve a labelled screen-reader action slot with stable ready, pending, retry, and unavailable geometry and reduced-motion-safe status.

Project and instrument collections use compact directory tables within one bordered surface rather than separate summary cards. The identity column contains the semantic resource icon, linked display name, and a distinct project or instrument ID when available. Project rows show Lead and Updated; instrument rows show Location, Owner, and Updated. Project Lead uses a bounded semantic column width so excess space remains available to the project identity. Missing API fields use `-`, and directory rows omit lifecycle badges and unsupported aggregate counts. Every project, instrument, sample, and dataset collection uses the shared 12rem Updated column at the trailing edge immediately before the shared Open action, including project- and instrument-scoped data, and retains that order when rows reflow on compact screens. Repeated project, owner, Updated, and Open cells use the shared resource collection cell components so compact labels, date formatting, person links, and navigation remain aligned. Project titles fall back to project ID, and instrument names fall back to instrument ID and then MFID.

Dialogs are focused input, alert dialogs destructive confirmation, sheets contextual details or filters, and popovers small anchored content. Every overlay has an accessible title and fitting description. Reversible confirmations such as publish and unpublish use `DismissibleConfirmationDialog` with Close, Escape, and outside-interaction dismissal. Consequential or destructive confirmations use `ConfirmationAlertDialog`. Feature code does not compose alert-dialog primitives directly. Both shared confirmations own pending locks, text-only footer actions, progress indication, and local errors. Dialog and alert-dialog surfaces stay within the dynamic viewport, own contained vertical scrolling, and keep their compact action footer visible while content scrolls. Footer actions remain aligned with the dialog content instead of creating a separate padded surface. Base UI owns focus containment, restoration, Escape, outside interaction, and scroll behavior unless a documented requirement differs. The application bar exposes QR scanning as a dedicated icon-only outlined action beside global search, with a persistent tooltip and accessible name. Its dialog has a bounded camera preview, live status, retry, camera switching when multiple devices are available, and an in-dialog text MFID or trusted-link fallback. Camera errors use plain guidance and retain the text fallback. Prefer a route for deep-linkable or durable navigation.

Resource management cards compose `ManagementAction` entries. A standalone entry uses the card presentation and a grouped Resource management card uses the row presentation. Feature code does not turn nested cards into rows by overriding their surface, ring, or radius.

The inspector is the route-addressable exception under [decision 0008](../decisions/0008-inspect-linked-resources-in-place.md) and uses one adaptive shadcn Sheet under [decision 0009](../decisions/0009-overlay-resource-inspection.md). It uses shared width, layer, surface, spacing, and motion roles, never resizes main content, and keeps Previous preview, Close, the title, and an Open full-page action stable. Relationship rows provide named preview and canonical navigation actions. Opening focuses its heading; following a relationship resets only panel scroll and focuses its new heading; closing restores the trigger or a stable page heading without restoring an older host-page scroll position. Target changes keep chrome mounted but never show old body under a new heading. Files and downloads remain full-page actions.

Resource graphs use Cytoscape inside a route-owned, bounded canvas with all dimensions, colors, line styles, zoom limits, and layout spacing resolved from semantic CSS tokens that Cytoscape can parse. The root has a stronger boundary, every node names its resource type in text, and association and lineage edges differ by line style, direction, and a visible text legend. Use a deterministic rightward layout without entrance animation. Node selection opens the shared overlay inspector above the unchanged canvas, while stable icon actions zoom in, zoom out, and fit the graph. A native table following the canvas stays expanded and provides equivalent keyboard-accessible relationship inspection and canonical navigation. The graph is never an editing surface or the only representation of provenance.

Feedback preserves page context. Skeletons replace only unreadable known shapes while stable page, section, and card headings remain visible. Loading, empty, unavailable, error, refreshing, stale, partial failure, disabled, selected, permission-limited, and destructive states are distinct and have accessible text. Refresh and pagination retain readable content with local busy and retry feedback. Placeholder data may bridge pagination within unchanged filters but must not present results from an incompatible filter, scope, type, or search as current. Errors stay in their affected panel, row, file, dialog, or field where possible; toasts never replace actionable or destructive feedback.

Entity section navigation places a default-size outlined Refresh action at the right edge of the tab row. Its tooltip exposes the browser-local time of the last successful read without changing row geometry. Contextual creation actions precede it on project and instrument pages and use the same default size. The action refreshes the primary entity representation and preserves readable detail on failure; independently loaded cards retain their own recovery. Dataset Processing uses the same single-page section hierarchy as Access management. Files and ingestion uses a normal card, monospaced copyable file MFIDs, text-labelled status badges, local pending and failure states, normalized local timestamps, and a contained multi-file request dialog with a stable footer. Request history is a full-width secondary surface within that card, with a small heading and count rather than nested navigation styling. Dataset processes uses a separate normal card and a compact empty state until supported work exists. Home places Recently viewed in its own card below recently added data. Both cards use one bounded resource-row component with the shared icon and name hierarchy, available project ID and MFID as icon-labelled supporting identity, the monospaced identifier role for the MFID, and a browser-local Created or Viewed timestamp opposite the identity. Recently viewed never persists browser history data. Search modes use the same filter-action treatment as resource types and expose selection through text and control state rather than color alone. Sample and dataset search identities show the project icon and project ID followed by a middle-dot separator and sample type or measurement on the same supporting line when the search response provides them.

## Accessibility, responsiveness, and validation

Target WCAG 2.2 AA. Every workflow is keyboard operable with logical focus and no trap; focus is visible and unobscured. Normal text meets 4.5:1 contrast, large text and meaningful boundaries or focus indicators 3:1. Support 200 percent zoom, text-spacing overrides, and reflow at 320 CSS px without two-dimensional page scrolling except bounded alternatives for tables and intrinsic scientific views. Meet target-size requirements, announce async status without stealing focus, provide correct landmarks, headings, labels, errors, table headers, and dialog semantics, and never require color, hover, drag, precise pointing, or animation. Graphs and scientific views require a textual or tabular essential-information alternative. Automated checks do not replace manual keyboard and screen-reader review.

Desktop and laptop are primary. Use their space for navigation, semantic tables, comparison, split views, contextual panels, and visible identity. Keep prose and form width bounded while allowing data and metadata workspaces to expand. Preserve routes and MFIDs across breakpoints, retain primary action and entity identity without page overflow, make column loss explicit and reversible, and never let sticky UI obscure focus or content. Test long names, full MFIDs, translation expansion, empty values, dense metadata, and permission-limited states.

Phase 0 requires a token and component fixture surface, automated rejection of raw colors, inline styles, arbitrary values, and primitive typography outside approved files, component semantic and keyboard coverage, light and dark visual baselines at compact, medium, and wide widths, automated contrast and accessibility checks, and manual critical-workflow review. Test loading, empty, error, stale, partial-failure, long, and dense states. The current fixture routes and Playwright baselines are specified in [`design-fixtures.md`](design-fixtures.md). Snapshot comparisons require identical dimensions and allow at most 500 differing pixels for cross-runner rasterization. Do not raise that bound to accept an unexplained change. Exceptions must promote a named missing semantic role; permanent unexplained suppressions are not accepted.
